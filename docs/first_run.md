# Первый запуск бейзлайна — 19.10.2026

Участок: `161_Курганы_32`, train. Вход: спутниковый GeoTIFF 880 × 781, четыре канала. Сам растр — EPSG:3857; UTM.json территории указывает UTM 37N (EPSG:32637). Веса организаторов, порог confidence 0.25, параметры `configs/baseline.json`.

Результат: технически успешный запуск на CPU. Модель сформировала один объект `pashni`; штатный фильтр исключил его из конкурсных классов. Итоговый GeoJSON пуст (0 объектов). Ошибок чтения/инференса в логе нет. Это не оценка качества модели и не конкурсный балл; GT не готовилась и метрика не рассчитывалась.

Измерения одного запуска на Ryzen 5 3500U:

- 25.343 с — процесс после старта мониторинга, включая импорт PyTorch;
- 14.850 с — вызов адаптера, включая импорт GIS/ML-зависимостей и загрузку модели;
- около 2.10 с — обработка единственного растра по логу;
- 561.4 МиБ — пиковый working set процесса (не вся память системы и не полное выделение виртуальной памяти);
- CPU, 2 потока PyTorch, без GPU.

Это один небольшой снимок: результаты нельзя переносить на крупные LAS и весь датасет. Участок входит в train; происхождение обучающей выборки исходных весов не проверено.

## Повторение на текущем компьютере

Из корня проекта:

```powershell
.\.venv\Scripts\python -X utf8 -u scripts/run_first_baseline.py
```

Команда действительно запускает инференс на фиксированном небольшом участке. Скрипт предназначен для первого локального smoke-run, а для других участков используйте общую команду `scripts/run.py predict`. Нужен psutil для замеров. Веса берутся из `vendor/organizer/baseline_solution/model.pt`, путь к датасету — из личных настроек.

Повторный запуск обновляет `results/first_run_161/report.json`, `run.log` и `predictions.geojson`. Сохраните их отдельно, если нужно сравнение разных запусков. Файлы результатов и окружение исключены из Git. Временные каталоги библиотек направлены в `tmp/` на диске проекта.

Ближайший следующий шаг — подготовить GT для этого участка и визуально сопоставить её со снимком. Нулевой результат пока фиксируем без подбора порогов по этому примеру.


## Проверка GT после первого запуска

Успешно прочитаны четыре Polygon класса повреждённых курганов. Геометрия валидна, все четыре находятся внутри снимка, положительных пересечений внутри класса нет. Построен `results/first_run_161/gt_partial/ground_truth_preview.png`. Все четыре эталонных объекта пропущены первым запуском.

Файл целых курганов `Курганы_32_SpOr_курганы_целые.geojson` не читается через Яндекс Диск (OSError 22). API публичной ссылки сообщает размер 3218 байт и MD5 `5e7cccf040a1d9db1ed2f7daafb4b69c`, но скачивание возвращает HTTP 500 с текстом `file IO failure: no successful lookup result`. Эту разметку не восстанавливали по предсказаниям или изображению. Итоговая метрика не рассчитана из-за неполной GT.

Добавлен `scripts/inspect_region.py`: нормализует разметку выбранного растра, проверяет геометрию и перекрытия, рисует контуры и при полной доступной GT вызывает официальный расчёт. Для текущей частичной проверки:

```powershell
.\.venv\Scripts\python -X utf8 scripts/inspect_region.py --region 161_Курганы_32 --modality sp_or --classes kurgany_povrezhdennye --predictions results/first_run_161/predictions.geojson --output-dir results/first_run_161/gt_partial
```

Без `--classes` требуется вся разметка участка. `--annotation-cache data/source_cache` позволяет использовать отдельно полученные файлы, сохраняя их относительные пути.

В нашем адаптере исправлен приоритет CRS для не-лидарных растров: сначала CRS самого GeoTIFF, затем UTM территории при отсутствии встроенного CRS. Исходный файл организаторов не менялся. Ошибка не объясняет отсутствие распознавания классов; она влияла бы на координаты ненулевых предсказаний. Проверена отдельным тестом.
