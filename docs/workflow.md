# Командное разбиение и первые команды

## Единое разбиение

`configs/splits/v1.json` — общий список train/validation/test. Участники используют файл из одного коммита. Один seed сам по себе недостаточен: входной каталог и правила группировки тоже должны совпадать.

- train — обучение модели.
- validation — выбор настроек, порогов и моделей.
- test — отложенная локальная оценка выбранного решения. Не используем для настройки.
- Закрытая проверка организаторов — отдельный набор, не наш test.

Папки исходного датасета не переносим и не размножаем. Код выбирает территории по списку. Новые тайлы в будущем должны наследовать часть выборки своей территории.

`configs/catalog/files.csv` — небольшой снимок прежнего inventory.csv: только относительные имена, размеры, признаки модальностей и классов. Содержимое снимков, геометрия и личные пути туда не входят. Этот файл и split передаём команде через Git.

Для создания первого каталога был использован существующий локальный inventory, без обращения к исходному датасету. Повторная генерация коллегам не нужна. При обновлении данных один участник обновляет каталог, согласует новую версию split и делает коммит.

## Как получено v1

Скрипт `splits.py` использует правила `configs/splits/policy.json` и seed 42. Связанные названия сгруппированы до разбиения: Гнёздово, Семибратнее, Судьбищи, номерные участки и другие семейства. Группы не пересекают части выборки. Целевая пропорция — 70/15/15; балансируются число территорий и наличие файлов разметки классов, не число объектов.

Гнёздово закреплено за train, Семибратнее за validation, Судьбищи за test, чтобы сохранить независимые группы с геофизикой. Серии с общими именами «Курганы», «Постройки», «Каменные выкладки» консервативно объединены и оставлены в train до уточнения географии.

Статус — предварительный. Названия не доказывают отсутствие географического пересечения. Позже проверим bounds/CRS и таблицу организаторов, пересечения объединим в группы и выпустим v2 при необходимости. Вхождение класса определяется именем файла; реальные объекты и пустые аннотации пока не проверены.

Электроразведка и термография по каталогу встречаются только в группе Гнёздово, поэтому в validation/test их сейчас нет. Такой split не измеряет качество переноса этих модальностей на новые территории. Для них потребуется отдельный протокол пространственной проверки после анализа покрытия; случайно дробить соседние профили ради наличия класса нельзя.

## Команды без чтения исходных данных

Из корня проекта, без установки ML-библиотек:

```powershell
python -X utf8 scripts/run.py plan --partition train --modalities sp_or --region 161_Курганы_32
python -X utf8 scripts/run.py plan --partition validation --output results/validation_files.json
python -X utf8 scripts/run.py predict --partition validation
python -X utf8 scripts/run.py train
```

План показывает список территорий, число файлов и заявленный объём. `--output` сохраняет полный перечень относительных путей. Это не скачиватель: выбранные файлы можно загрузить на том компьютере, где будет выполняться работа. Можно передавать `--region` несколько раз.

Коллеге достаточно клонировать репозиторий, настроить свой `dataset_root` и получить нужную часть исходных данных из разрешённого командного источника. Полный набор не обязан проходить через компьютер автора репозитория. Разделение по спискам вообще не требует загрузки LAS/GeoTIFF и больших объёмов RAM.

Генерация новой версии по небольшому каталогу (не запускать просто ради клонирования):

```powershell
python -X utf8 scripts/run.py split --output configs/splits/v2.json
```

Перед этим обновить `version` и правила в policy. Каталог и policy хешируются в split. Существующий файл без `--overwrite` не заменяется.

## Первый инференс, когда выбрано оборудование

Адаптер использует функции исходного бейзлайна из `vendor/organizer`, загружает модель один раз и обрабатывает выбранные территории последовательно. Полигоны записываются в итоговый файл по мере обработки; копировать исходные папки не нужно. Однако внутри оригинального бейзлайна массивы рельефа и растры могут быть большими: небольшой размер файла на диске не гарантирует низкий расход RAM. На слабом ПК начните с небольшой территории со спутниковым растром.

Получить веса из архива организаторов и положить в `models/baseline.pt`, либо явно передать `--weights`. Веса не скачиваются автоматически. Бейзлайн по умолчанию обрабатывает LAS, ортофото и спутник; геофизика и историческое аэрофото не покрыты этим стартовым адаптером.

На выбранном вычислительном компьютере можно установить `python -m pip install -e ".[baseline]"`. Это незакреплённый набор зависимостей по импортам исходного примера; GPU/CUDA и совместимость версий нужно проверить отдельно. Альтернатива — предоставленное организаторами окружение `wooferclaw/archeology:latest`. В этой работе зависимости не устанавливались и реальный GPU-инференс не запускался.

Команда ниже уже запускает обработку (без `--execute` только показывает план):

```powershell
python -X utf8 scripts/run.py predict --partition train --region 161_Курганы_32 --execute
```

`configs/baseline.json` задаёт параметры. Это стартовая конфигурация, а не оптимизированный для слабого ПК режим.

## Метрика

`evaluation.py` вызывает официальный расчёт. Нужны предсказания и уже подготовленная объединённая GT-разметка в EPSG:3857 с `class_name` и `region_name`. Сырые отдельные GeoJSON ещё требуют нормализации, согласования объединения пересечений и проверки CRS — эта стадия пока не реализована. Оценка по произвольно склеенной разметке не гарантирует совпадения с платформой.

```powershell
python -m pip install -e ".[evaluation]"
python scripts/run.py evaluate --partition validation --predictions results/baseline/predictions.geojson --ground-truth data/processed/validation_gt.geojson
```

Команда отклоняет объекты без известных классов/территорий и файлы с территориями другой части. Пустые предсказания допустимы. Для полноценной оценки GT должна покрывать всю выбранную часть; не сравнивайте предсказания одного участка с GT всей validation.

## Обучение и платформа

`training.py` и `configs/train.json` — явный шаблон. Показывают train/validation и параметры, а `--execute` завершается с объяснением недостающей подготовки и backend. Фиктивное обучение не выполняется.

`inference/main.py INPUT_DIR OUTPUT_FILE` запускает адаптер на всех территориях переданного конкурсного входа, без фильтра train/validation/test. Выход — путь к GeoJSON-файлу. Для будущей посылки понадобятся код, конфиги, подходящее окружение и веса. Архив для отправки ещё не собран и на платформе не проверен.

Проверки каркаса без исходных данных и ML-зависимостей:

```powershell
python -m unittest discover -s tests -v
```
